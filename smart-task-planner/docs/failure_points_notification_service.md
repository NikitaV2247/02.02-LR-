# Локальные точки отказа — Notification Service

- **Автор:** С. Ветрова (Backend-разработчик Notification Service)
- **Дата:** 2026-09-14
- **Связанный документ:** `API_CONTRACT.md`, раздел 5 (политика доставки со стороны Task Service)

## 1. Что эмулируется в рамках лабораторной

Полноценная подписка на шину событий (Message Broker) заменена HTTP-вебхуком:
Task Service после успешного создания задачи сам вызывает наш эндпоинт
`POST /api/webhooks/task_created`. Уведомление пользователю эмулируется записью
в лог-консоль (`logging`, stdout). Это осознанное упрощение: сервис остаётся
stateless и не зависит от инфраструктуры.

## 2. Реестр локальных точек отказа

| # | Точка отказа | Условие возникновения | Поведение сервиса | Смягчение |
|---|---|---|---|---|
| Н-1 | Невалидное тело вебхука | JSON не соответствует схеме `Task` (нет `title`, неизвестный `status` и т.п.) | FastAPI/Pydantic возвращает `422`, уведомление не создаётся, сервис не падает | Отправитель (Task Service) трактует любой не-2xx как сбой попытки и делает повтор по политике доставки (контракт, разд. 5) |
| Н-2 | Пик нагрузки | Много одновременных событий task.created | Каждый запрос обрабатывается синхронно; при перегрузке возможны таймауты у отправителя | У отправителя есть retry с backoff; в проде — настоящий брокер (RabbitMQ/Kafka) с очередью на нашей стороне |
| Н-3 | Недоступность потока вывода | Редкий кейс: закрыт/переполнен stdout | `logging` буферизует запись и не роняет обработчик запроса | В проде — отправка в реальный канал (email/push) с собственным ретраем |
| Н-4 | Зависимость от Task Service | Task Service не вызывает вебхук (упал до отправки) | Событие вообще не доходит до нас — «тихая» потеря уведомления | Лог `WEBHOOK_FAILED` на стороне Task Service позволяет выявить потерю и дослать событие вручную/скриптом |

## 3. Вывод

Сервис спроектирован так, чтобы любая единичная ошибка обработки запроса
не выводила его из строя: ошибка валидации — это `422` по контракту, а не crash;
сбой канала вывода изолирован внутри logging. Критической внешней точкой
является только Н-4 (невызванный вебхук), и она компенсируется журналированием
на стороне отправителя.
