# Локальные точки отказа — Task Service

- **Автор:** Орлов М.С. и Баикин К.А. (Backend-разработчик Task Service)
- **Дата:** 2026-09-14
- **Связанный документ:** `API_CONTRACT.md`, раздел 5 (политика доставки вебхука)

## 1. Роль модуля в сквозном сценарии

Task Service — точка входа клиента (CRUD задач) и ИНИЦИАТОР события
`task.created`. Сбои этого модуля влияют на обе функции, поэтому обработка
ошибок строится по правилу: «операция с задачей важнее уведомления» —
задача должна сохраниться, даже если доставка события не удалась.

## 2. Реестр локальных точек отказа

| # | Точка отказа | Условие возникновения | Поведение модуля | Смягчение |
|---|---|---|---|---|
| Т-1 | Файл SQLite недоступен | Нет прав/места на диске, повреждение файла `task_service/data/tasks.db` | `sqlite3.Error` → FastAPI возвращает `500` на конкретный запрос, процесс жив | `GET /health` для диагностики; БД пересоздаётся при перезапуске |
| Т-2 | Notification Service недоступен | Сервис не поднят, сеть недоступна, соединение отклонено | `WEBHOOK_RETRY` с backoff 1/2/4 c (до 3 попыток), затем `WEBHOOK_FAILED` в лог; создание задачи НЕ откатывается (201 уже отдан) | Очередь в памяти + retry; в проде — персистентный брокер |
| Т-3 | Перезапуск процесса при непустой очереди | Упал/перезапущен Task Service, пока в очереди есть события | События в очереди в памяти теряются | Журнал `WEBHOOK_QUEUED`/`WEBHOOK_FAILED` позволяет выявить потерю и дослать вручную; в проде — персистентная очередь |
| Т-4 | Медленный получатель | Notification Service отвечает дольше таймаута (5 c) | Попытка считается неуспешной (`httpx.TimeoutException` — подкласс `httpx.HTTPError`) → retry по обычной политике | Таймаут меньше, чем время жизни HTTP-запроса клиента |
| Т-5 | Невалидный ответ получателя | Не-2xx (например, `422` при рассинхронизации схем) | Трактуется как сбой попытки (`WEBHOOK_RETRY`) — из-за этого инцидента в контракте закреплена точная схема тела вебхука (разд. 5) | Contract-first: обе стороны валидируют одну и ту же схему Task |

## 3. Почему создание задачи не откатывается при сбое вебхука

Событие ставится в очередь ТОЛЬКО после успешной фиксации задачи в БД,
а клиент уже получает `201`. Откатывать сохранённую задачу из-за недоступности
уведомлений означало бы нарушать принцип «уведомление — best-effort».
Компенсация — журналирование `WEBHOOK_FAILED` и (в проде) реконсиляция
по логам или персистентная очередь с гарантией at-least-once.
