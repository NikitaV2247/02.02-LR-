# API Contract — «Умный планировщик задач»

- **Версия:** 1.0 (утверждён)
- **Дата:** 2026-09-14
- **Статус:** согласован командой 2026-09-14 по итогам разрешения конфликта в разделе 5 (см. REPORT.md)

## 1. Общие соглашения

- Формат обмена: JSON (UTF-8).
- Коды ошибок: `422` — ошибка валидации тела запроса; `404` — объект не найден; `500` — внутренняя ошибка сервиса.
- Дата/время: ISO 8601 (UTC), пример: `2026-09-14T07:15:30+00:00`.
- Идентификаторы: UUID v4 в строковом представлении.

## 2. Схема данных Task

| Поле | Тип | Описание |
|---|---|---|
| `id` | string (UUID) | Генерируется Task Service при создании |
| `title` | string (1..200) | Название задачи |
| `description` | string | Описание задачи (может быть пустым) |
| `status` | enum: `new`, `in_progress`, `done` | Статус задачи, по умолчанию `new` |
| `created_at` | string (ISO 8601) | Генерируется Task Service при создании |

## 3. Task Service

### 3.1. POST /api/tasks

- **Запрос:** JSON тела задачи **без** `id` и `created_at`:
  ```json
  { "title": "Купить молоко", "description": "2 литра" }
  ```
- **Ответ:** `201 Created` + созданная задача со всеми полями.
- **Ошибки:** `422` — валидация (например, пустой `title`).

### 3.2. Дополнительные эндпоинты Task Service

| Метод и путь | Успех | Ошибки | Назначение |
|---|---|---|---|
| `GET /api/tasks` | `200` | — | Список задач (опционально `?status=new`) |
| `GET /api/tasks/{id}` | `200` | `404` | Получить задачу |
| `PUT /api/tasks/{id}` | `200` | `404`, `422` | Изменить поля задачи |
| `DELETE /api/tasks/{id}` | `204` | `404` | Удалить задачу |
| `GET /health` | `200` | — | Проверка живости сервиса |

## 4. Notification Service

### 4.1. POST /api/webhooks/task_created

- **Назначение:** приём события «создана новая задача».
- **Запрос:** JSON объекта Task (см. раздел 2).
- **Ответ:** `200 OK`.
- **Ошибки:** `422` — тело не соответствует схеме Task.
- Полученный объект фиксируется уведомлением (в рамках лабораторной — запись в консоль).
- Дополнительно: `GET /health` → `200 OK`.

## 5. Формат сообщения вебхука (финальная версия — результат разрешения конфликта)

- **Метод:** `POST` на `{NOTIFICATION_SERVICE_URL}/api/webhooks/task_created`
  (по умолчанию `http://localhost:8002/api/webhooks/task_created`)
- **Заголовки:**
  - `Content-Type: application/json`
  - `X-Event-Type: task.created` — идентификатор типа события для фильтрации на стороне получателя
- **Тело запроса:** **объект Task целиком** — ровно тот JSON, который вернул `POST /api/tasks` (без обёртки/конверта):

  ```json
  {
    "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
    "title": "Купить молоко",
    "description": "2 литра",
    "status": "new",
    "created_at": "2026-09-14T07:15:30+00:00"
  }
  ```

- **Политика доставки со стороны Task Service:**
  - таймаут запроса: 5 c;
  - повторные попытки: до 3, задержка 1/2/4 c (экспоненциальный backoff);
  - при исчерпании попыток — запись `WEBHOOK_FAILED` в лог Task Service; задача при этом НЕ откатывается (уведомление — best-effort).

- **Ответ:** `200 OK`

> **Решение команды (2026-09-14):** тело вебхука — объект Task, как в п. 4.1
> («Принимает JSON объекта Task»); это позволяет Notification Service валидировать
> вебхук той же схемой без вложенных моделей. Метаданные события передаются
> заголовком `X-Event-Type` (идея Д. Орлова сохранена в упрощённом виде).
> Конверт `{event, occurred_at, task}` отклонён как избыточный при одном типе
> событий. Политика доставки принята из предложения Task Service без изменений.
> Версия контракта повышена 0.1 → 1.0. Обе стороны приводят код к данной версии.
